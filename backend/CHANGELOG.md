# Backend changelog

## Unreleased

- **Breakpoint editing, Pause and Step Out** (MIS-500). `setBreakpoints` after `configurationDone` replaces one source's set: paused, the Robot thread applies and verifies it before the reply; running, the reply is `verified: false` with a pending message and the set applies at the next keyword start, followed by `breakpoint` `changed` events for the latest generation only. Unchanged entries keep their IDs; removed IDs are never reused; at most 64 replacements may wait. `pause` stops before the next keyword RF actually runs (never NOT RUN, `Run Keyword` inner duplicates or console/condition evaluation) with `reason: "pause"`; blocking library code is not interrupted, which a `console` output line says. `stepOut` leaves the user keyword whose body holds the current line, by invocation (recursion and same-line calls are distinct; `Run Keyword` frames are passed over), and stops before the caller's next keyword; at test/suite level it fails with an explicit message and the worker stays paused. The worker's control channel now has one pump thread (select-based reader, bounded stop) and the Robot thread drains its queue at each keyword start. New required live suite `test_dap_controls_live.py` (18 cases) on both runtime rows. The merged MIS-441 integration's capability pin now includes the conditional breakpoint and logpoint capabilities this backend advertises.
- Windows mixed-debug parent shutdown now cancels an idle child DAP reader without waiting on a buffered socket read; real socket tests cover cancellation with an open peer and fragmented Unicode frames. Windows API dependencies load at DAP startup so module initialization is separate from failed-launch resource measurements; repeated-attempt leak and no-fallback assertions are unchanged.

- Repair Windows preview conformance paths (MIS-434): the authenticated readiness message supplies the actual worker interpreter PID for debugpy handoff, reaped Windows process handles close explicitly, and failure-path resource tests remain mandatory. The live driver captures backend creation identity before shutdown; bounded listener refusal still requires an explicit refusal (never a timeout), Unicode harness output is explicit UTF-8, and Robot console checks preserve native line endings. Qualification belongs to the exact-SHA full release receipt; the historical full Windows run 39283871806 failed and remains evidence.

- **Windows preparation** (MIS-434 preview qualification). File URIs as VS Code writes them on Windows (`file:///c%3A/My%20Tests/a.robot`) now map to drive paths; previously they became the driveless `\c:\...`. UNC, device and driveless URIs are refused on Windows. Discovery and workspace walks no longer follow Windows junctions. A quick fix whose target is on another drive is not offered, instead of failing the request. The Robot worker writes UTF-8 to its output pipes, matching how the adapter decodes them; previously non-ASCII console output was garbled on Windows. The release harness runs on Windows too: each command runs in its own Job Object, venv `Scripts` paths are used, and a minimal Windows environment is passed. The live suites observe processes through `tests/processes.py` (Linux `/proc`, Windows Toolhelp32 snapshot) and have Windows equivalents for the POSIX-only cases. All suites use explicit UTF-8 text I/O. A new LSP case covers VS Code-form URIs, a folder with a space, and CRLF line/column mapping; discovery covers junctions, an unreadable file, long paths and Windows URI refusals. Verified so far: both Linux rows, plus one Windows CI run of build/install/`doctor`, the transport suite and selected harness cases (16 pass); the later full Windows run 39283871806 executed every suite and failed, as retained in the issue; only a new exact-SHA successful receipt qualifies a repaired candidate.
- **Supported runtime matrix** (MIS-433): the backend now runs on Python 3.11 with Robot Framework 7.3.2 as well as Python 3.13 with RF 7.5, both with debugpy 1.8.22 and the optional Robocop 9.1.0, verified on Linux aarch64 only (Windows qualification is MIS-434). `pyproject.toml` declares exactly these rows (`requires-python = ">=3.11,!=3.12.*,<3.14"`, `robotframework==7.3.2; python_version == "3.11"` / `robotframework==7.5; python_version == "3.13"`), `constraints.txt` pins each row, and the new `runtime.SUPPORTED` gate refuses every other Python/RF combination in the LSP, discovery and DAP worker with a message naming the interpreter, its versions and the supported set (previously LSP/discovery only refused a missing RF and the worker accepted any RF 7.5.x). `doctor` adds the interpreter path and a `runtime` record (row, `supported`, `supportedRows`) and exits 2 for an unsupported row.
- The 3.11 row follows RF 7.3.2 where RF itself differs: RF's number lookup is called with RF 7.3.2's API (discovery labels with `${1e3}` crashed the request on RF 7.3.2); `${TEST METADATA}` is a run-time built-in only on RF 7.5 (it was missing there and is an undefined variable on RF 7.3.2, as RF 7.3.2 fails on it); RF 7.3.2's ROBOT-format standard-library documentation is shown escaped. The listener, keyword creation for module libraries, parser model classes, test-name/template handling and the other built-ins are identical in both releases (checked against both sources). Class/dynamic-library limits are unchanged on both rows.
- `verify_release.py` accepts `--python <interpreter>` to select a runtime row (instead of refusing every Python but 3.13), checks it against the committed source's supported rows, records `interpreter`, `supportedRows`, `doctor`, `row` and `workerInterpreter` (the paused Robot worker's `/proc` argv[0]/executable, which must be the installed backend's `sys.executable`) in `release.json`. `test_lsp_live.py` gains 2 cases for unsupported-row refusals and `doctor`; `test_lsp_diagnostics_live.py` now has 25 cases; live tests assert a supported row instead of RF 7.5. The discovery depth test removes its 1,100-level tree itself, because Python 3.11's `shutil.rmtree` recurses per level.
- The debug adapter's worker control/event exchange no longer uses inherited file descriptors (`pass_fds`). It runs over one private loopback TCP connection (`control.py`, standard library only): the adapter listens on `127.0.0.1` with an OS-allocated port, passes the port in the worker's argv (`--control-port`) and a random 32-byte session secret as one line on the worker's stdin pipe (then closed), and both ends prove the secret with HMAC-SHA256 over fresh nonces from each side, so the secret is never in argv, the environment or on the socket. Other connections are closed and reported as `important` output (`Refused an unauthenticated Robot worker control connection: ...`); after the worker is authenticated the listener is closed. The worker protocol messages are unchanged. A worker that does not connect fails `launch` with `Robot worker did not open its control channel (worker exit code N)`. New `process_tree.py` owns start and stop of the Robot worker and the debugpy adapter: POSIX keeps a new session/process group with SIGTERM and SIGKILL after 5 seconds; leftover group members get SIGKILL while the exited leader is still unreaped (`os.waitid` with `WNOWAIT`), so a reused group ID is never signalled (now also for the debugpy adapter's group and after a run ends by itself); Windows starts the child suspended with `CREATE_NEW_PROCESS_GROUP`, assigns it to a kill-on-close Job Object through ctypes before resuming it, and stops with `TerminateJobObject`. Control handshakes have one 2-second bound each and refusal output is capped after ten. No runtime module references `os.killpg`/`signal.SIGKILL` at import time any more (`dap.py` did in a default argument). A worker that ends by a signal or with an exit status above 255 without being stopped is reported (`Robot worker crashed: terminated by SIGKILL`) before `exited`/`terminated`; failed cleanup is sent as `important` output (`... cleanup failed: ...`), logged on stderr, and makes the `dap` service exit 5. New required suites `test_process_tree.py` (21 tests) and `test_dap_process_live.py` (6 real-process cases: foreign connections refused, worker crash reported, whole tree including a grandchild killed) run in the release harness; all existing suites pass unchanged. Verified with Python 3.13.7, Robot Framework 7.5, debugpy 1.8.22 and Robocop 9.1.0 on Linux (RobotCode absent). **The Windows code paths are not Windows-verified**: they have never run (no Windows substrate, MIS-431); only their pure logic and an import of every runtime module with `sys.platform` `win32` and POSIX-only names removed are checked on Linux. Leak checks still use Linux `/proc`; a Windows process-snapshot equivalent belongs to the Windows qualification outcome (MIS-434). Windows is not supported by this release; this entry left `requires-python` and the RF/debugpy pins unchanged (the runtime rows above are MIS-433).
- The debug adapter now supports conditional Robot breakpoints and logpoints and advertises `supportsConditionalBreakpoints` and `supportsLogPoints`. A `SourceBreakpoint.condition` is evaluated by the listener on the Robot execution thread when the call on that line starts, with RF 7.5's IF/WHILE condition semantics in the current variable context (`$iteration == 2`, `${count} > 2`); false continues, true stops as before. A `logMessage` emits a DAP `output` event (category `console`, with source and line) and never stops; `{expression}`, `${}`, `@{}`, `&{}` and `%{}` parts are rendered from the live context, `{{`/`}}` are literal braces, a failing part renders as `<error: ...>` and messages are cut at 65,536 characters. Empty or syntactically invalid conditions and malformed messages are `verified: false` with the reason at `configurationDone`; a condition that raises at run time emits an `important` output and does not stop; non-string `condition`/`logMessage` fail the request. Breakpoints, plain ones included, no longer hit a keyword RF reports but does not run (NOT RUN, e.g. the untaken side of an inline `IF`), nor a second time for the inner keyword of `Run Keyword    Log    x`; recursive calls on one line still hit each time. Stepping is unchanged. `hitCondition` remains refused (now `Hit-count breakpoints (hitCondition) are unsupported`), and breakpoint changes after configuration remain unsupported. New required live suite `test_dap_conditional_live.py` (5 cases) runs in the release harness. Verified with Python 3.13.7, Robot Framework 7.5, debugpy 1.8.22 and Robocop 9.1.0 (RobotCode absent).
- Added LSP semantic tokens (`semantic_tokens.py`): `initialize` advertises `semanticTokensProvider` with a documented legend, `full: true` and `range: true` (no `full/delta`), and `textDocument/semanticTokens/full` and `/range` return LSP 3.17 relative data in 0-based lines and UTF-16 code units. Token types: `namespace` (section headers), `property` (setting names), `class` (test/task names), `function` (user keyword names and keyword calls, including setup/teardown/template keyword cells), `variable` (`${}` `@{}` `&{}` `%{}`, also embedded in names and arguments), `comment`, `keyword` (control-structure markers), `macro` (English BDD prefixes) and `operator` (`...`); modifiers `declaration`, the custom `resolved` (a call that resolves with definition's import-aware resolution to a location, exactly when definition returns one, so AuditLibrary.py's `Build Record` is resolved and an unimported AShadow.py or nonexistent keyword is not) and `defaultLibrary` (RF standard-library keywords). Tokens come from RF 7.5's own model and `search_variable`, never a line scan; a BDD prefix is split off only when the full name matches no keyword, as in RF. Parsing errors keep the tokens of the parsable parts, RF `ERROR` tokens, unrecognized headers and invalid statements get none, and tokens are mapped back to LSP lines where RF also breaks lines (U+2028, form feeds). A range request returns only tokens completely inside the range; every request reflects the current overlay. Not tokenized: import names, plain arguments, `$name` in expressions, call qualifiers, `Run Keyword` arguments. A leading byte order mark (dropped by RF, counted by LSP) shifts first-line tokens by one unit. New required live suite `test_lsp_semantic_tokens_live.py` (9 cases with exact expected tokens) runs in the release harness; `doctor` lists it. Verified with Python 3.13.7, Robot Framework 7.5, debugpy 1.8.22 and Robocop 9.1.0 (RobotCode absent). Next candidates: `full/delta`, inlay hints.
- Plain public top-level functions of a statically readable module library are now library keywords, as RF 7.5 makes them: `def ring_bell()` is `Ring Bell` (RF's `printable_name`) with its location, arguments and docstring, for definition, hover, completion, signature help, references, the import quick fix and diagnostics. One shared AST reading (`module_reading`) decides both the indexed keywords and the names a library may also expose. A literal `__all__` (by Python name, also for `@keyword` functions), `ROBOT_AUTO_KEYWORDS = False` and `@not_keyword` are honoured, so a name RF hides is now an `unknown-keyword` error; two libraries defining `ring_bell` (or one `@keyword("Ring Bell")`) now get the `ambiguity` warning and qualify fixes. Nothing is guessed: a name bound or used otherwise at module level (import, assignment, conditional definition, other decorator, `register(fn)`) only silences unknown-keyword errors, and a class/dynamic library, computed `__all__`/`ROBOT_AUTO_KEYWORDS`, `keyword(...)(fn)` at import time or `setattr`/`globals()`/`sys.modules` writes leave the module's keywords open. Same-library duplicates (`ring_bell` and `ringBell`) are not indexed. Argument counts are no longer checked for a library keyword under `Set Library Search Order`, or when another library may expose the name without indexing it. A guarded `@keyword("X")`, a literal `fn.robot_name = "X"` and a name a function declares `global` now also silence unknown-keyword errors. Known gaps: imported/assigned-name collisions are not reported as ambiguous; a library failing to import at run time still counts as defining its keywords; an imported function with its own `@keyword` name is still known only by its Python name (unchanged). `test_lsp_diagnostics_live.py` now has 24 cases, each new fixture also run with RF 7.5.
- Added a `discovery` service (`robot-companion-backend discovery`, descriptor entry `services.discovery`) implementing Robot Companion's normalized discovery API v1 over stdio JSON-RPC with LSP framing: `initialize` advertises `robotCompanionDiscovery.version` 1 and `robotCompanion/discoverTests` returns the workspace's `.robot` file suites with their tests and UTF-16 ranges, so Test Explorer needs no RobotCode. Files are walked by RF's directory rules (`_`/`.` prefixes and `CVS` ignored, symbolic links not followed) and built with RF 7.5's own reader, parser and `TestSuite.from_model` with the `__init__.robot` test defaults; nothing is executed, and a `language:` line naming a Python module is reported instead of imported. Tests tagged `robot:exclude` (also through init `Test Tags`) are left out, as RF leaves them out. Test labels are the names RF runs, with variables of the file's own Variables section, static built-ins and RF's number variables resolved by RF's `replace_string`; other variables stay as written. Ranges count lines as LSP clients do, also where RF breaks lines at U+2028 or form feeds. Parsing errors keep the tests RF builds, unreadable files are omitted, and both are reported in an additive `errors` array and on stderr; a non-file, relative or `..` workspace URI returns -32602. Every request rereads the workspace. New required live suite `test_discovery_live.py` (9 cases) compares the result with `robot --dryrun` on the audit corpus plus a nested fixture and runs in the release harness. The test client gained an optional `env`; `FramedStream` an outgoing size bound per service (discovery replies up to 64 MiB); diagnostics recognise `__INIT__.robot` as an init file case-insensitively, as RF does. Verified with Python 3.13.7, Robot Framework 7.5, debugpy 1.8.22 and Robocop 9.1.0 (RobotCode absent). Next backend candidates: debug robustness, per-test result streaming.
- Variable references and rename follow loop-carried values: a use in a `FOR`/`WHILE` body (or `WHILE` condition, nested loops included) that assigns a local of the same name anywhere in the body is reached by that local on later iterations, so it is a reference of both that local and the definition visible at its line (such as the suite variable). Rename changes both definitions and all their uses together, so the renamed suite runs the same with RF 7.5 (MIS-359's `${MODE}=    IF    True    Catenate    ${MODE}-x` repro no longer fails after renaming); it is refused with `RequestFailed` and no edit when a built-in or a suite variable defined in several imported files reaches the loop use. Uses outside such loops, definition and hover are unchanged. `test_lsp_navigation_live.py` now has 13 cases.
- Added broader diagnostics (`diagnostics.py`), published on open/change with UTF-16 ranges on the offending cell: RF 7.5's own parsing and model errors (now including invalid section headers, parsed with RF's resource/init loaders where they apply) as errors, and deprecated syntax (singular headers, `[Return]`) as warnings, as RF reports it; a keyword call that resolves to nothing in the import-aware scope as an error naming the keyword (an AShadow.py-only keyword is unknown); an ambiguous call as a **warning** (was an error) naming each source; argument counts the resolved signature cannot accept as errors, with RF's dry-run resolver and message; and undefined `${variable}` uses in test/keyword bodies as warnings. Each rule skips what cannot be known statically (class/dynamic/unmodelled libraries, `Import Library`, `Set Library Search Order`, variable files, variable-setting Python code, embedded or `@{}`/`&{}` arguments), and variables set dynamically anywhere in the workspace (`Set Test/Suite/Global Variable` as calls, settings or `Run Keyword` arguments, `VAR scope=...`) are never reported. Import diagnostics now cover the import's name cell.
- Added `textDocument/codeAction` quick fixes, advertised as `codeActionProvider` (`quickfix`) for clients with CodeAction literal support: import the only workspace resource or library file that defines an unknown keyword (never a guess between several files), and qualify an ambiguous call with a library/resource name.
- Added `textDocument/formatting` with Robocop 9.1.0's default formatters (new optional `format` extra, pinned in `constraints.txt`), advertised as `documentFormattingProvider` only when Robocop 9.1.0 is importable. Formatting is line-based TextEdits, deterministic (workspace Robocop configuration is not read), idempotent and keeps `\r\n` line endings. `doctor` reports the formatter; the release runner installs the extra and records it in `release.json`.
- New required live suite `test_lsp_diagnostics_live.py` (15 cases) runs in the release harness. Verified with Python 3.13.7, Robot Framework 7.5, debugpy 1.8.22 and Robocop 9.1.0 (RobotCode absent). Next backend candidates: test discovery/results API, debug robustness, range formatting.
- Added `textDocument/references`, `textDocument/prepareRename`/`textDocument/rename`, `textDocument/documentSymbol` and `workspace/symbol` (`navigation.py`), advertised in `initialize` (`renameProvider` with `prepareProvider`). Keywords are identified by their resolved definition, so references to AuditLibrary.py's `Build Record` include `Audit.Build Record` and never AShadow.py, same-named own keywords or ambiguous calls. Variable references and rename stay in the variable's scope. Rename edits a `.robot`/`.resource` user keyword's definition and every resolved call, keeping library/resource and BDD prefixes; Python library and standard-library keywords, ambiguous targets, embedded-argument keywords and built-in variables are refused with an LSP `RequestFailed` error. Variable uses include `$name` in conditions, `${{ }}` and BuiltIn's evaluating keywords, and an argument's `name=` cells in calls passing it by name; escaped `\${name}` is literal. Variables nested in `${{ }}`, in a variable name (`${greeting_${lang}}`) and in item access are found with RF's own variable search, and an inline IF assignment is visible only after its branch runs (also for definition and hover). New names are validated (one cell, no control-structure marker), and prepareRename reports the same refusals as rename. Document symbols are hierarchical (variables, tests/tasks, keywords with argument/local children; flat for clients without hierarchy support); workspace symbols find tests and keywords in unopened files. The `initialize` workspace folders are scanned on every request, so `didChange` and files created/changed/deleted on disk are reflected without a restart. New required live suite `test_lsp_navigation_live.py` (12 cases) runs in the release harness. Verified with Python 3.13.7, Robot Framework 7.5 and debugpy 1.8.22 (RobotCode absent). Next backend candidates: formatting and code actions, broader diagnostics, test discovery/results, `Run Keyword` arguments and Python library keyword rename.
- Keyword cells of `[Setup]`, `[Teardown]`, `[Template]`, `Suite Setup`/`Teardown`, `Test`/`Task Setup`/`Teardown` and `Test Template` now resolve for definition and hover (and references/rename); `NONE` is no keyword.
- One English BDD prefix (`Given`, `When`, `Then`, `And`, `But`) is ignored when the full call name matches no keyword, as in RF, for definition, hover, signature help and the new requests.
- Hover on a Python library keyword without a return annotation (`def other(x):`) no longer shows a false `Returns None`; `-> None` still shows `Returns None`.
- Hover and definition on a typed variable definition cell (`${PORT: int}    8080`, `${n: int}=    Set Variable    1`) now find that variable, as for its later uses.
- Accepting a variable completion inside an extended-syntax name (`${rec|ord.name}`, `${rec|ord[0]}`) keeps the suffix: the edit replaces only the sigil and base name. Without a closing `}` nothing after the cursor is replaced.
- Signature help splits `name=value` with RF's own rule, so `=` inside a variable, item access or inline expression (`Multi Step    ${{1 == 1}}`) is a positional value, not `**options`.
- Added `textDocument/hover`, `textDocument/completion` and `textDocument/signatureHelp`, advertised in `initialize` (completion `resolveProvider: false`, no snippets). They share definition's import-aware resolution, so unimported libraries (AShadow.py) never contribute. Hover shows keyword origin, RF-formatted arguments, return annotation and documentation, and variable source plus only statically written values. Completion offers keywords in call cells with their origin and scoped variables after `${`, with UTF-16 edit ranges. Signature help tracks positional, `name=value`, varargs and kwargs arguments. Markdown is used only when the client asks for it; workspace documentation is escaped. New required live suite `test_lsp_features_live.py` (15 cases) runs in the release harness.
- Standard-library and implicit BuiltIn keywords are now indexed from RF's own libdoc (Remote and unimportable libraries excepted), so they resolve for definition, hover, completion and signature help, below custom libraries as in RF.
- Variables now also resolve to imported resources' Variables sections, embedded keyword arguments, `FOR` and `EXCEPT AS` variables; a `VAR` value no longer counts as a definition of the variables it refers to.
- The `lsp` service removes its cwd from `sys.path` at start, and standard-library indexing does so again, so neither RF itself (`robot.py`) nor optional imports (XML's `lxml`, Screenshot's `wx`) can execute a same-named workspace module when the server runs as `python -m`.
- A variable used in a call's arguments resolves to its definition before that call (`${x}=    Set Variable    ${x}`), for definition and hover.
- A Python library whose function header cannot be located becomes an import diagnostic instead of failing every request for the importing file.
- A module-name library's namespace is its full module name (`company.robot.Helpers.Keyword`), not the text before its last dot.
- A position on the empty line after a final line break is accepted instead of failing.
- Standard-library imports (`Library    Collections`, `OperatingSystem`, ...) no longer produce an error diagnostic; as in RF, they win over a sibling file of the same name. Other module-name libraries without a sibling file (`a.b.C` → `a/b/C.py`, open buffer or disk) get an Information diagnostic `Library not resolved in this version: <name>`. Missing `.py`/path imports remain errors.
- LSP error replies carry the plain message instead of the `(code, message)` tuple repr.
- `scripts/build_dists.py` writes no `__pycache__` into the source checkout; the README's direct pip build sets `PYTHONDONTWRITEBYTECODE=1` for the same reason.

## 0.1.0.dev1 — phase-1 vertical slice

- Ran the live LSP, Robot DAP and mixed Robot/debugpy suites against the approved offline runtime (Python 3.13.7, RF 7.5, debugpy 1.8.22, RobotCode absent).
- Fixed the Robot worker: `run_cli` takes no listener instance, so the worker now parses the CLI with RF's public parser and adds its in-process listener before executing.
- Fixed Python child connection loss: a failing final flush of the lost socket no longer aborts cleanup, so `terminated` and the session `end` event are still sent.
- Repinned debugpy to the approved 1.8.22 (was 1.8.17, which the approved wheel set does not contain).
- Replaced the setuptools build with a dependency-free, reproducible in-tree PEP 517 backend and a minimal frontend; the release runner requires pip's rebuild from the sdist to be byte-identical. `doctor` no longer reports build tools as runtime requirements.
- Added bounded stdio framing, an explicit runtime probe and a standalone Python distribution definition.
- Added the LSP for parser/import-based navigation, current document overlays and limited syntax/import/ambiguity diagnostics.
- Added a `dap` service: a stdio DAP lifecycle subset with one owned Robot worker process group, an explicit RF prerequisite error, recorded unverified breakpoints and terminate/disconnect cleanup.
- Added the paused-thread RF listener for breakpoint verification, stack/scopes/variables, continue/next/stepIn and live Robot keyword console calls, with a required real-process DAP suite.
- Fixed private pipe cleanup when a worker fails to spawn; lifecycle checks cover real failed launches and reject unavailable Linux process observation.
- Added Python handoff v1 with an owned debugpy adapter, loopback child DAP connection, same-worker attachment and mixed-session cleanup, with six real-process conformance cases.
- Added an offline standalone build/install and conformance runner with source/hash/count receipts, isolated frontend-free venv execution and bounded owned-process cleanup.
- Copied the synthetic v1 audit corpus and added real-subprocess transport and language conformance drivers.

Exact-SHA release results are recorded in the issue `artifact-handoff`, not here.
